## 项目状态

`project-state.json` 必须记录：

- 当前阶段、Proposal Owner、项目 ID。
- 资料审计、Grill Me、提案策划书、需求、策略、目录、`AGENTS.md`、品牌官方视觉资料、品牌视觉审计、内容冻结、初始样张、设计语言校准集、`DESIGN.md`、内容 QA、视觉 QA 的批准人、时间和确认记录 ID。
- 每章页面列表与逐页确认状态；一次性全稿审查报告、独立审查 Agent ID 和确认记录。
- 页面重开记录；`reopened_by` 必须等于 Proposal Owner。
- 当前内容冻结 ID 和设计版本。
- 最终PPT页面数量、页序哈希、最终页序批准记录、讲稿飞书文档、讲稿状态和讲稿确认记录。
- 品牌官方视觉资料的来源 ID、项目内相对路径、品牌身份范围决定、审计文件和 `DESIGN.md` 融合记录。
- `design_calibration.path`、必需样张类型、真实 Alpha 校准样本、逐页确认记录和当前 `design_version`。
- `assembly.manifest_path`、每个正式页面的明确确认记录、批准 PNG、内容哈希、设计版本和最终拼装批准记录。

## 设计语言校准门禁

视觉方向阶段不能只提交方向说明。每个候选方向必须：

1. 有不同于其他方向的视觉命题，不以换色冒充新方向；
2. 实际调用 Image2 生成至少一张代表页视觉稿；
3. 在 `project-state.json.visual_direction.directions` 登记 `direction_id`、名称、视觉命题、`visual_family_id`、代表页和 `image2_assets`；
4. 每个 `image2_assets` 条目登记 `generator: image2`、项目内资产路径和提示词记录；
5. Owner 从这些真实视觉稿中选择 `selected_direction_id`，并让 `approval_record_id` 与批准记录一致。

方向说明、Moodboard、纯 HTML/CSS 版式草图、无实际生成资产的提示词包都不能批准 `visual_direction`，也不能进入 `design_calibration`。Image2 不可用时可以准备方向和提示词，但阶段必须保持未通过。

初始视觉方向确认后，先创建独立 `deck/design-calibration.html`，不得直接生成正式章节。校准档位、最低样张数、风险覆盖与透明 PNG 校准规则统一见 [design-calibration-contract.md](design-calibration-contract.md)，本文件不重复数字。

在 Codex 浏览器中逐页批注。全部样张确认后记录 `approvals.design_calibration`，再把其规则编译进 `DESIGN.md` 和 `design-tokens.json`。校准集固定设计语言，不固定每一张正文页的具体构图。校准目标是用最少页面覆盖主要设计风险，不按固定十页清单机械出图。

## 按章节生成

- `DESIGN.md` 和设计令牌批准后，先按页面合同确定路线。HTML页使用 `python scripts/render_deck.py <项目目录> --chapter-id <章节ID>` 与 `node scripts/capture_review_pngs.mjs <项目目录> --chapter-id <章节ID>`；图像原生页由 Image2 直接生成 16:9 PNG，并放入 `deck/review/`，通过 Codex 浏览器原生评论完成批注。
- 同一批次的所有章节必须使用同一个 `design_version`、页面合同和资产规则。
- 正文页可在弹性合同内选择版式、密度和媒体比例；不得改写字体体系、色卡、品牌符号、网格、安全区或组件语法。
- 内容修改只重建受影响章节；`DESIGN.md`、设计令牌或公共组件改变时，全部章节输出过期并必须重建。
- 单章评审循环只使用 HTML＋PNG或直出PNG＋Codex浏览器原生评论，不生成 PDF/PPT。单章评审完成不等于页面确认，也不等于最终导出完成。

## 页面确认与拼装准备库

1. 评论解决、视觉 QA 通过或 Agent 判断可用，都不能自动确认页面。
2. 只有 Proposal Owner 明确下达“确认本页”“确认这些页面”或同等含义命令，Agent 才运行 `manage_assembly_ready.py approve`。
3. 批准记录写入 `deck/assembly-ready/manifest.json`，至少包含 `slide_id`、批准内容哈希、`content_freeze_id`、`design_version`、`source_type`、源文件、批准 PNG、文件哈希、确认人、时间与确认记录 ID。
4. 批准 PNG 复制到 `deck/assembly-ready/pages/`，作为最终拼装的页面快照；后续修改回到该页记录的 HTML 或 direct PNG 源。
5. 页面重开、内容哈希改变、`design_version` 改变或批准资产变化时，运行 `manage_assembly_ready.py reopen`，撤回该页拼装准备状态。
6. 全部正式 `slide_id` 均已确认且版本一致后，Proposal Owner 仍需明确下达“全部内容确认，开始拼装”；Agent 才运行 `manage_assembly_ready.py finalize`。
7. 最终 PPT/PDF 从拼装准备库按 `deck-spec.json` 页序一次性组装。评审期间不得为了查看修改效果重复拼装 PPT/PDF。
8. 需要可编辑文字层时，仍以同一批准 PNG 为视觉基准；从对应 HTML 捕获实测文字框、字体与颜色，编译为 PowerPoint 原生文字。字段 QA 、坐标 QA 和备注回查只证明编译忠实；必须另外渲染全案，对照批准 PNG 检查字体替代、换行、遮挡与视觉节奏。

## 项目启动 Grill Me

背景资料进入 `inputs/client/` 后，调用 `grill-me-lite` Skill：

1. 先从资料中提取事实，不向用户重复询问可查事实。
2. 一次只问一个决策问题，并给出推荐答案及理由。
3. 只追问会改变策略、范围、承诺或交付的事项；通常为 3—8 个关键问题，不为覆盖固定题库而延长访谈。
4. 每个答案写入 `content/proposal-brief.md` 的决定记录；存在冲突时继续追问，不静默替用户选择。
5. 用户明确确认已经达成共同理解后，记录 `brief_grill`；策划书全文再次确认后记录 `proposal_brief`。
6. 若 `Visualize:visualize` 可用，可将决策树、依赖关系、范围或评审路径做成确认视图。不得因为插件不可用而阻塞；Markdown 策划书始终是权威文件。

提案策划书未确认时，不研究策略主张，不生成正式目录，不进入页面内容生产。

## 策略立场与说服力门禁

策略目录前必须按 [proposal-persuasion-gate.md](proposal-persuasion-gate.md) 生成并确认策略立场卡，至少包括：

- 品牌面对的确定性机会与核心矛盾。
- 对行业、消费者、产品和经营方式作出的鲜明判断。
- 品牌当前选择为什么正确。
- 全案主动选择的策略路径和明确放弃的平庸路径。
- 希望客户最终作出的决策。
- 从开场到结尾的情绪曲线，以及每个章节承担的情绪任务。

缺少其中任何一项，不得用客观资料目录或并列功能模块代替。事实核验与风险治理在内部层执行；只有会推翻核心策略或客户承诺的问题才阻塞对外创作。

完成策略立场卡后，必须继续按 [strategy-continuity-contract.md](strategy-continuity-contract.md) 编译：

1. 总策略因果句；
2. 章节策略接口表；
3. 章节标题链；
4. 每章页面论证链；
5. 全案页面标题链。

不得按标书模块分别生成章节后再拼接。目录确认前先隐藏正文朗读章节标题；逐章确认前朗读本章页面标题；内容冻结前朗读全案标题。任何层级可以任意换序、需要依赖“下面进入……”才能连接，或无法回溯到总策略时，均退回重构。

## 整章批量成稿与飞书逐页确认

PPT内容生产采用“骨架按章确认、正文整章生成、飞书逐页确认”：

1. 先确认本章 `strategy_input`、`chapter_claim`、页面论证链、标题链、`strategy_output` 和 `next_chapter_necessity`。
2. 按 [feishu-proposal-draft-format.md](feishu-proposal-draft-format.md) 一次生成本章所有页面的完整提案初稿，包括核心内容、逻辑展开、上屏内容、讲解方向、策略过桥、视觉生成建议、证据和页面五项说服力字段；不生成完整讲稿。
3. 整章生成必须沿用已确认页序和标题链，不得重新发明结构或把页面改成并列模块。
4. 将整章写入项目主飞书提案文档，以稳定 `slide_id` 作为页面标题锚点；不得为每章创建分散文档。本地 Markdown 只承担同步快照和灾备，不得成为内容确认的权威母版。
5. 每轮写入后必须重新抓取整份飞书文档，保存为 `content/feishu/proposal-draft.md`，并在 `project-state.json.proposal_draft` 记录文档 URL、`document_id`、正整数 revision、回读时间、快照 SHA256 和当前已确认页面顺序。
6. 对回读快照执行格式校验：每章必须包含“本章回答、逻辑路径、情绪方向”；每页必须包含“核心内容、逻辑展开、PPT上屏内容、讲解方向、策略与过桥、视觉生成建议、证据与来源”。
7. 连续朗读整章，检查策略、标题、证据、语言、情绪和转场。
8. 团队在飞书逐页评论和确认；Agent 读取新增评论后，只重写受影响页面及必要转场。修改后再次执行整份文档回读、快照和格式校验。
9. 修改改变本章 `strategy_output` 时，下一章 `strategy_input` 自动过期并重新检查。

“逐页确认”是审批粒度，不是生成粒度。禁止为每一页单独启动一次内容生成；只有完整脚本、关键创意或重大争议页需要单页深挖时例外。

飞书不可用时可以先写入本地结构化 Markdown，但必须将 `proposal_draft.status` 标记为 `local_fallback_pending_sync` 并记录 `fallback_reason`。该状态只允许继续本地起草，不得将章节登记为已确认，不得进入一次性全稿审查、内容冻结或视觉生产。恢复后必须同步到原飞书母稿并完成整份回读，才能改为 `verified`。

## 最终PPT确认后的讲稿生成

完整讲稿是最终PPT的派生产物，不参与策略草稿、章节骨架、PPT内容稿或视觉设计阶段。

1. 等待所有正式PPT页面完成内容与视觉确认。
2. 按批准页面生成最终清单，锁定最终页码、页序、`slide_id`、标题和批准PNG。
3. Proposal Owner 确认不再调整顺序、拆页和合页后，才启动讲稿生成。
4. 一次性读取全案最终PPT，按页面顺序生成完整讲稿，不按章节分别独立生成。
5. 每页讲稿必须引用最终页码和 `slide_id`，解释当前画面并自然承接前后页面。
6. 写入飞书后回读开头、中间章节交界和结尾，验证页码、标题、页数与转场。
7. 全案连续朗读并由 Owner 确认。
8. 页面发生换序、拆分、合并、标题或核心内容修改时，对应页面及前后转场讲稿自动过期并重建。

## 品牌官方视觉资料门禁

正式视觉方向前必须：

1. 用户把品牌手册、官网视觉截图、官方 KV、Logo 文件、官方色卡或官方模板上传到 `inputs/brand-official/`。
2. 在 `project-state.json.brand_visual` 登记非空 `source_ids` 与对应 `source_files`；文件必须是项目内相对路径。
3. 记录 `scope_decision`、`project_brand_name`；若为视觉代理，再记录 `reference_brand_name`。
4. 将可核验的视觉符号、Logo 规则、字体、色卡、图形、材质、摄影语言、版式特征与禁忌写入 `evidence/brand-visual-audit.md`。
5. 明确区分“官方明确”“从官方画面采样”“本案提议”。不得把采样色值或 Agent 推断冒充官方规范。
6. Owner 分别批准资料范围和视觉审计。`DESIGN.md` 必须引用全部来源 ID；生成前再批准品牌视觉融合记录。

## 一次性全稿成稿完整性审查

所有章节全部页面逐页确认后，只创建一次新的审查 Agent，并强制读取 [full-draft-integrity-redteam.md](full-draft-integrity-redteam.md)。只提供完成结构检查所需材料：

- 客户标书和正式资料。
- 当前项目 `AGENTS.md`。
- 已确认策略与目录。
- 全稿逐页内容与稳定 `slide_id`。
- 全部章节策略接口和最终目录。

同时明确告知：Proposal Owner 已确认的事实、策略、数据、案例、表达强度和场外取舍均为只读权威，不得质疑。客户标书只用于检查漏项与承接位置，不用于重新评价品牌决策。

审查 Agent 不得外部搜索，不读取证据账本，不做资料充分性、安全、法务、合规、舆情或风险判断，不提出替代策略。要求只输出：

1. `BLOCKER`：不修复就不能冻结。
2. `MAJOR`：会降低比稿说服力或执行可信度。
3. `MINOR`：表达和页间衔接问题。
4. `PASS`：经检查无问题的维度。

只检查五个维度：

1. 策略逻辑与章节接口。
2. 标题链、表达力度与自然度。
3. 页间、章间衔接和情绪流。
4. 拆页、合页与信息密度。
5. 视觉锤、主载体与Image2/HTML生产可行性。

标书漏项、占位符、内部备注和项目文件内部直接矛盾可以标记；不得延伸为资料、风险或策略评价。完整讲稿的朗读检查后置到 `speaker_notes` 阶段。

全稿审查同时增加检查：

- 目录与实际页序一致。
- 同一核心策略贯穿所有章节。
- 公司介绍保持前置且没有侵入正式策略。
- 重要结论在后文得到执行承接。
- 不同章节没有重复争夺同一演讲任务。
- 标书响应可被评审快速定位。
- 演讲任务、证据、页面和附录的 `slide_id` 一致；最终讲稿生成后再执行讲稿映射检查。

同时按 [cross-page-semantic-qa.md](cross-page-semantic-qa.md) 检查：

- 每页是否回答前页形成的问题，并为下一页创造真实需要。
- 每页是否提供新问题、新证据、新判断、新选择、新动作或新验证。
- 标题句式、视觉母题、人物、骨架和固定组件的重复是否承担新的语义角色。
- 连续播放与全案 montage 是否暴露断链、重复、疲劳、跳跃或章节任务冲突。

跨页统计只作为线索；经人工复核确认的语义断链和无增量重复属于内容问题，必须在冻结前修复。

## 缺失信息处理

- 能局部推进时，继续不受影响的章节并记录缺口。
- 缺口影响策略主线、报价、资源承诺、关键数字或客户合规口径时，阻塞受影响阶段。
- 不在客户可见页面写“待确认”。未解决内容不得进入冻结稿。

## 页面重开

内容冻结后发现问题时：

1. Owner 创建重开记录并指定 `slide_id`、原因和影响范围。
2. 将受影响页面及所有下游页面标为过期。
3. 修改章节源稿，对受影响页及其章节接口执行主 Agent 内容复核；若改变全案策略输出或章节关系，则重新执行一次性全稿审查。
4. 重新冻结并生成新的冻结 ID。
5. 从拼装准备库撤回受影响页面，重建 HTML 和评审 PNG，重新取得明确页面确认。
6. 禁止直接补丁批准 PNG、最终 PDF 或 PPT。
