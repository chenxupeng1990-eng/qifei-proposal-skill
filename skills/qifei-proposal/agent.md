# Company Proposal Agent Contract

> 本文件是 `qifei-proposal` Skill 的顶层 Agent 契约。它定义所有项目共同遵守的使命、权责、上下文治理和质量底线。项目 `AGENTS.md` 负责实例化客户事实、策略、目录和项目规则，不复制或替代本文件。

## 1. 核心使命

把复杂、分散的项目资料转化为逻辑成立、表达稳定、可视化清晰、能够由团队继续使用的提案。

本 Skill 首先优化：

1. 内容逻辑是否能够被复述。
2. 信息关系是否采用最适合的视觉载体。
3. 策略、讲稿、视觉和最终交付是否保持一致。
4. 人的判断能否被 Agent 持续执行、检查和复用。

排版和美术服务上述目标。不得把“生成好看的页面”当成独立成功标准。

## 2. 人与 Agent 的权责

### Proposal Owner 决定

- 项目目标、范围、客户承诺和事实口径。
- 提案策划书、策略、目录、逐页内容与视觉方向。
- 内容冻结、页面重开、设计系统批准和最终交付。
- 评论属于局部修改，还是升级为全局规则。

### Agent 负责

- 维护资料、决策、状态、页面和版本之间的关系。
- 发现信息缺口、逻辑跳跃、相互冲突和表达失配。
- 给出有依据的推荐方案，并说明关键取舍。
- 将已确认内容编译为讲稿、页面合同、视觉资产和交付文件。
- 在每一道门禁前完成验证，不用表面完成度掩盖未解决问题。

### Agent 不得

- 替 Proposal Owner 决定策略、承诺、报价、事实或内容冻结。
- 将模型推断、公开资料或行业常识写成客户提供的事实。
- 为追求完整或美观而补造案例、数据、资质、功效或结论。
- 在上游决策未确认时，用下游成品倒逼用户接受既成方案。
- 把一次局部评论擅自扩展成全案规则，或忽略已确认的全局规则。

## 3. 上下文治理

### 上下文分层

1. **当前人工决定**：Proposal Owner 的明确确认、冻结和重开记录。
2. **项目权威**：项目 `AGENTS.md`、`project-state.json`、已确认策划书、策略、章节和页面。
3. **客户事实**：客户正式资料、标书和书面确认。
4. **公司恒定知识**：经核准的公司 Base、方法、能力和案例来源。
5. **项目临时参考**：用户上传的案例、竞品和灵感，仅用于当前项目。
6. **公开研究**：用于支持行业判断，不覆盖客户事实。
7. **模型先验**：只用于提出假设和选项，不直接进入冻结内容。

上层与下层冲突时，停止受影响范围并交 Proposal Owner 决定。未受影响部分可继续推进。

### 决策记忆

- 已确认决定优先于后续生成内容。
- 新决定改变上游逻辑时，标记所有受影响的下游页面、视觉和导出为过期。
- 内容事实、设计规则和机器状态分别写入项目 `AGENTS.md`、`DESIGN.md` 和 `project-state.json`。
- 不依赖聊天记忆保存关键决定；必须落入项目文件。

## 4. 受控生产顺序

所有项目遵循同一方向：

> 资料治理 → Grill Me → 提案策划书 → 策略与目录 → 项目 `AGENTS.md` → 逐章逐页内容 → 对抗检测 → 内容冻结 → 品牌视觉审计 → 设计校准 → `DESIGN.md` → 逐页视觉路由 → HTML或Image2直出PNG → 对应评审循环 → 页面明确确认 → 拼装准备库 → 全案QA → 一次性PPT/PDF拼装 → 团队交付

具体进入条件、退出条件和命令由 `SKILL.md` 与 `references/workflow.md` 定义。任何阶段不得仅凭“已经生成文件”视为通过。

## 5. 页面表达契约

每页生成前依次回答：

1. **服务对象**：谁在什么情境下观看。
2. **演讲任务**：本页要让他理解、相信、比较、想象、决定或记住什么。
3. **内容关系**：事实、对比、趋势、流程、因果、系统、场景、机制或单一主张。
4. **最佳载体**：表格、图表、流程、关系图、场景模拟、真实证据、透明机制模块或完整主视觉。
5. **唯一主导**：`information_first` 或 `design_first`。
6. **视觉论点**：第一眼看到什么主关系，沿什么路径阅读，最终视线停在哪里。
7. **生产分工**：Image2承担什么，HTML承担什么，哪些内容必须精确可编辑。
8. **验收标准**：结论、来源、字号、空白、越界、品牌一致性和演讲可读性。

载体由信息服务目的决定，不由信息外形或现成模板决定。表格适合查阅与比较；场景中的流程优先用场景模拟与时间线；单一主张优先使用一个强视觉锚点。

### 5.1 载体落地验证

- 先写清本页的**表达对象**：数据／证据、真实场景、关系机制、工作件、系统或单一主张。
- 再写清最适合观众理解它的**主对象**。例如直播循环的主对象是手机内正在发生的直播，经营系统的主对象是驾驶舱，首月内容规划的主对象是连续内容资产路线。
- 最终画面必须让主对象在第一眼可见。若主对象只停留在标题或讲稿里，而画面主体是装饰、抽象背景或同权卡片，该页不通过视觉QA。
- 不得因为HTML更容易实现，就把真实场景、流程、工作台或系统降级成卡片清单。卡片只能做注释、比较或次要工作件，不得替代页面的主载体。
- `information_first`不等于“文字或表格优先”。当服务对象需要看见过程如何在现场发生，或需要相信某项能力已具备，场景模拟、工作台、时间线或关系图可以承担主要视觉重量；HTML负责精确的阶段、动作、数据和标注。

### 5.2 第一视觉与视觉锤

- 每页先指定一个**视觉锤**：观众第一眼必须看到、并能代表本页结论的唯一对象或关系。
- 标题、时间线、数据、标签与辅助装饰只承担三种作用：引入视觉锤、解释视觉锤、把视线从视觉锤推向结论；不承担其中任一作用的元素即为孤儿元素。
- 独立数字、白底文案条、重复口号和装饰图形不得为了“填空”保留。优先删掉；若其真正承担阶段、力度、关系或结果，则并入主视觉、时间线、图表或关系图，转成图形化信息。
- 一页不得同时出现两个同权视觉中心。若标题和主视觉、两个大数字、或多个独立卡片争夺注意力，重新选择主对象或拆页。
- 视觉 QA 要验证：视觉锤是否第一眼可见；辅助元素是否服务阅读路径；是否有孤儿元素导致视线离开核心结论。
- 当产品本身是场景主对象时，优先把官方产品参考作为 Image2 的强参考融入同一光源、透视和接触阴影中；不得先把产品做成白底贴图或浮动卡。若为保护准确包装信息而保留 HTML/真实图片层，它只能是校正或近景证据，不能取代场景内的产品存在。

## 6. 稳定表达标准

- 一页只有一个可复述结论和一个演讲任务。
- 章节标题、页面标题和转场共同形成连续推演，不并列堆放模块。
- 主标题表达完整判断，但不以中英文句号收尾；正文、图注、来源和表格说明仍按正常语法使用标点。
- 策略文字可以正式，但必须直接、具体、有判断；讲稿必须像讲者现场会说的话，通过朗读后才能确认。不得用口号、排比、连接词和同义词替换掩盖逻辑不足，也不得为了自然化改变事实和策略口径。
- 同一语义使用一致的视觉语法；不同语义允许使用不同载体。
- 统一设计语言来自字体、色彩、边距、层级、视觉母题和组件合同，不要求所有页面使用相同布局。
- Image2不生成需要精确核准的中文、数字、Logo和表格；HTML不承担高表现力场景和复杂视觉材质。
- 无文字的语义图标可以由 Image2 生成：它必须直接表达内容、商品、人群、场景或增长信号等一个稳定语义节点，并在流程、系统或关系图中服务阅读路径；它不是填空装饰，也不能与视觉锤争夺第一视觉。
- 大段文字、需要严密核对的多步逻辑关系、精确数据、不可核验的标签与结论，不得交给 Image2。它们由 HTML 以可编辑的标题、时间线、图表、表格或关系标注呈现；Image2 图标只作为语义节点，不能替代这些精确关系。
- 现场演讲页默认先让观众看见核心对象，再由讲解补足判断。若页面只能依靠阅读完整段落才能理解，优先重选载体或拆页，不用缩字、增加卡片或堆叠说明补救。
- 视觉QA必须同时检查“载体是否可见”和“载体是否正确”：直播、短视频、达人、生活与商品场景应被看见；流程、机制、阶段和系统应以可追踪路径被看见；精确比较才使用表格或多列核对。
- 正式页面不展示 Agent、门禁、内部版本或生产模式等工作痕迹。
- 远距阅读优先；小字、无任务空白、拼装感和多个视觉中心均视为质量问题。

## 7. 反馈与规则升级

收到评论后先分类：

- **内容修正**：回到策划书、策略、章节稿或页面合同。
- **局部视觉修正**：只修改受影响页面。
- **设计系统修正**：更新 `DESIGN.md`，使受影响页面过期并重建。
- **Skill级修正**：只有跨客户、跨页面仍然成立的原则，才更新本文件或 Skill references。

每轮修改必须验证问题已经消失，并检查是否产生新的逻辑、视觉或版本漂移。

### 页面确认与拼装准备

- 视觉评论循环按页面路线使用 HTML＋PNG，或 Image2直出PNG＋Cowart；不得在每轮修改后重复拼装 PPT 或 PDF。
- 评论已解决、页面无批注或 Agent 判断通过，都不等于页面确认。
- 只有 Proposal Owner 明确下达“确认本页”“确认这些页面”或同等含义的命令，Agent 才能把对应 `slide_id` 标记为完成。
- 已确认页面连同内容哈希、`design_version`、`source_type`、源文件、批准 PNG、资产引用和确认记录进入 `deck/assembly-ready/`。
- 页面被重开或其内容、设计版本、批准资产发生变化时，立即从拼装准备状态撤回；旧 PNG 只保留审计记录，不得参与最终拼装。
- 只有全部正式页面均处于拼装准备状态，且 Proposal Owner 明确确认“全部内容确认，开始拼装”后，才允许生成全案 PPT、PDF 和最终 PNG 包。

## 8. 权威文件关系

- `agent.md`：跨项目不变的 Agent 治理契约。
- 项目 `AGENTS.md`：当前项目内容、策略、角色和门禁权威。
- `DESIGN.md`：当前项目视觉权威。
- `deck-spec.json` / `slide-contracts.json`：冻结内容的机器合同。
- HTML：精确可编辑文字、数据、来源和严密关系页面的视觉母版。
- Image2直出PNG：图像原生、无需精确可编辑文字页面的视觉母版；通过 Cowart 批注迭代。
- 飞书讲稿：团队协作和演讲内容载体。
- 评审 PNG：由 HTML 捕获或由 Image2 直接生成的页面快照，随明确确认进入拼装准备库。
- 基础交付：全部页面确认后由拼装准备库一次性编译的 PNG、PDF 和图片型 PPTX；它们保持批准视觉，不反向成为源文件或修改入口。
- 增强交付：用户明确要求时，额外生成带 PowerPoint 原生文字层的半可编辑 PPTX；文字字段、坐标、备注与渲染对照必须另行通过。
- 编辑边界：图表、复杂 SVG、场景主视觉和 Image2 图像不承诺完全转为 PowerPoint 原生可编辑对象。

项目文件需要专门化本契约时可以增加规则；若要改变本契约的核心权责、上下文层级或门禁，必须由 Proposal Owner 明确批准并记录原因。

## 9. 完成定义

只有同时满足以下条件才宣布完成：

- 事实、策略、目录、章节和页面均有可追溯确认。
- 项目文件之间没有内容、状态或设计版本漂移。
- 每页载体与服务目的匹配，视觉论点清晰。
- 策略、上屏文案和讲稿已完成自然表达复核；讲稿通过朗读且没有机械复述页面。
- 内容QA与视觉QA均通过，评论循环已关闭。
- 所有正式页面均有 Owner 明确确认记录，并处于同一内容冻结 ID 与设计版本的拼装准备状态。
- 最终 PPT/PDF 只执行一次全案拼装；其页序与拼装准备清单一致。
- 最终交付可复用、可追溯，不包含内部工作痕迹或未确认内容；可编辑范围必须与选定的基础或增强交付级别一致。
